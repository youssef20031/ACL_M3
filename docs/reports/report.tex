\begin{abstract}
This report presents the design, implementation, and evaluation of \textbf{FPL FantasyTrivia}, a sophisticated Retrieval-Augmented Generation (RAG) system specifically engineered for Fantasy Premier League (FPL) analytics. The system integrates a Neo4j knowledge graph containing comprehensive football statistics with state-of-the-art Large Language Models (LLMs) through a novel hybrid retrieval architecture. By synergistically combining parameterized Cypher queries for structured data retrieval with semantic embedding-based search using Sentence Transformers, the system delivers accurate, context-aware responses to diverse user queries. Our architecture supports multiple retrieval strategies---Baseline, Embeddings, and Hybrid---enabling flexible trade-offs between precision and semantic understanding. The system demonstrates robust performance across statistical analysis, player comparisons, transfer recommendations, and interactive trivia generation. Comprehensive evaluation across five LLM models (Gemma-2-2b, Mistral-7B, Llama-3.1-8B, Zephyr-7B, and Qwen-2.5-72B) validates the effectiveness of our approach in grounding LLM responses with verified knowledge graph data.
\end{abstract}

\section{Introduction}
%==============================================================================

\subsection{Motivation and Problem Statement}
Fantasy Premier League (FPL) is one of the world's most popular fantasy sports platforms, engaging over 11 million managers globally who make weekly strategic decisions based on complex player statistics, fixture difficulty, team form, and transfer market dynamics \cite{fpl_official}. Traditional FPL analytics tools present raw data in tabular formats, requiring users to perform significant manual analysis to extract actionable insights.

The emergence of Large Language Models presents an opportunity to democratize access to complex sports analytics through natural language interfaces. However, LLMs trained on general corpora often exhibit \textit{hallucination}---generating plausible but factually incorrect responses when queried about specific, up-to-date statistics. This limitation is particularly problematic in the FPL domain, where decisions based on incorrect data can directly impact user outcomes.

\subsection{Proposed Solution}
\textbf{FPL FantasyTrivia} addresses these challenges by implementing a Graph-RAG (Retrieval-Augmented Generation with Knowledge Graphs) architecture that grounds LLM responses in structured, verifiable data. Our key contributions include:

\begin{enumerate}
    \item A comprehensive Neo4j knowledge graph schema capturing players, teams, fixtures, gameweeks, and seasons with rich statistical relationships
    \item A multi-modal retrieval system supporting Cypher-based queries, embedding-based semantic search, and hybrid approaches
    \item Robust Natural Language Understanding (NLU) pipeline with rule-based intent classification and spaCy-powered entity extraction
    \item Interactive trivia generation system leveraging knowledge graph facts
    \item Comparative evaluation framework for multiple LLM backends
\end{enumerate}

\subsubsection{Presentation Layer}
The \textbf{Streamlit UI} (\texttt{app.py}, 1,263 lines) serves as the primary user interface, providing:

    \item Multi-tab interface: Q\&A Assistant, FantasyTrivia, Player Search, Player Comparison, Model Comparison
    \item Real-time session state management for conversation history
    \item Interactive graph visualizations using NetworkX and Plotly
    \item Configurable retrieval mode and LLM model selection
    \item Knowledge graph context display for transparency
\end{itemize}

\subsubsection{Preprocessing Layer}
The NLU pipeline comprises two specialized components:

\begin{description}
    \item[Intent Classifier] (\texttt{preprocessing/intent\_classifier.py}, 332 lines): Rule-based classification supporting 16 distinct intents including \texttt{PLAYER\_STATS}, \texttt{PLAYER\_COMPARISON}, \texttt{TOP\_SCORERS}, \texttt{TEAM\_ANALYSIS}, \texttt{RECOMMENDATION}, and \texttt{TRIVIA}.

\end{description}

\subsubsection{Data Layer}
\begin{description}
    \item[Neo4j Knowledge Graph] (\texttt{graph/} module): Stores structured FPL data with nodes for Players, Teams, Positions, Seasons, Gameweeks, and Fixtures connected through typed relationships.
    
    \item[Vector Store] (\texttt{embeddings/} module): In-memory storage of player embeddings using Sentence Transformers for semantic similarity search.
\end{description}

\subsubsection{Intelligence Layer}
\begin{description}
    \item[LLM Manager] (\texttt{llm/llm\_manager.py}, 539 lines): Manages interactions with HuggingFace Inference API, supporting multiple model backends including Gemma-2-2b, Mistral-7B-Instruct, and Llama-3.1-8B-Instruct.
    
    \item[Prompt Builder] (within \texttt{llm/}): Constructs structured prompts with context injection, persona specification, and fallback handling.
\end{description}

\subsection{Knowledge Graph Construction}

\subsubsection{Schema Design}
The Neo4j knowledge graph schema is designed to capture the relational structure of FPL data while enabling efficient traversal for complex queries. Table~\ref{tab:schema} details the node types and their properties.

\begin{table}[H]
\centering
\caption{Knowledge Graph Node Types and Properties}
\label{tab:schema}
\begin{tabular}{@{}lll@{}}
\toprule
\textbf{Node Type} & \textbf{Key Properties} & \textbf{Description} \\
\midrule
\texttt{Player} & id, name, web\_name & Individual footballer record \\
\texttt{Team} & id, name, short\_name & Premier League club \\
\texttt{Position} & id, name (GK/DEF/MID/FWD) & Playing position category \\
\texttt{Season} & id (e.g., ``2022-23'') & FPL season identifier \\
\texttt{Gameweek} & number, deadline\_time & Weekly matchday \\
\texttt{Fixture} & id, home\_score, away\_score & Individual match record \\
\bottomrule
\end{tabular}
\end{table}

\subsubsection{Relationship Types}
The graph captures the following relationships:

\begin{itemize}
    \item \texttt{(:Player)-[:PLAYS\_FOR]->(:Team)}: Player's current team affiliation
    \item \texttt{(:Player)-[:PLAYS\_POSITION]->(:Position)}: Player's designated position
    \item \texttt{(:Player)-[:PLAYED\_IN \{stats\}]->(:Fixture)}: Performance in a specific match with embedded statistics (goals, assists, points, minutes, bonus, etc.)
    \item \texttt{(:Fixture)-[:PART\_OF]->(:Gameweek)}: Match's gameweek assignment
    \item \texttt{(:Gameweek)-[:IN\_SEASON]->(:Season)}: Gameweek's season membership
    \item \texttt{(:Fixture)-[:HOME\_TEAM]->(:Team)}: Home team for a fixture
    \item \texttt{(:Fixture)-[:AWAY\_TEAM]->(:Team)}: Away team for a fixture
\end{itemize}

This schema enables rich historical analysis, such as tracking a player's performance trajectory across different teams, seasons, and positions.

\subsubsection{Query Library}
The \texttt{CypherQueries} class (\texttt{graph/queries.py}, 916 lines) contains over 20 parameterized query templates for various FPL operations:

\begin{lstlisting}[language=SQL, caption={Example Cypher Query: Top Scorers by Season}]
MATCH (p:Player)-[r:PLAYED_IN]->(f:Fixture)
MATCH (f)-[:PART_OF]->(gw:Gameweek)-[:IN_SEASON]->(s:Season {id: $season})
WITH p, SUM(r.goals_scored) AS total_goals
RETURN p.name AS player, total_goals
ORDER BY total_goals DESC
LIMIT $limit
\end{lstlisting}

Key query categories include:
\begin{itemize}
    \item Statistical aggregations (top scorers, assisters, bonus points)
    \item Player-specific queries (season stats, gameweek performance)
    \item Team analysis (top performers, fixture results)
    \item Comparative queries (player-to-player, head-to-head)
    \item Value analysis (points per million, most selected)
\end{itemize}

\subsubsection{Entity Extraction}
The \texttt{EntityExtractor} leverages spaCy's Named Entity Recognition (NER) augmented with custom patterns and gazetteers. The extraction process involves:

\begin{enumerate}
    \item \textbf{Team Recognition}: Matching against a comprehensive gazetteer of 40+ team name variations (e.g., ``Arsenal'', ``Gunners'', ``ARS'')
    \item \textbf{Player Recognition}: Using spaCy's PERSON entities combined with a dynamically loaded set of known players from the knowledge graph
    \item \textbf{Position Detection}: Pattern matching for position terms (``goalkeeper'', ``GK'', ``midfielder'', ``MID'', etc.)
    \item \textbf{Season Extraction}: Regex patterns for season formats (``2022-23'', ``22/23'', ``last season'')
    \item \textbf{Gameweek Extraction}: Patterns for gameweek references (``GW10'', ``gameweek 10'', ``week 15'')
    \item \textbf{Statistical Terms}: Matching for stat types (``goals'', ``assists'', ``points'', ``bonus'')
\end{enumerate}

\section{Retrieval Strategies}
\label{sec:retrieval}
%==============================================================================

The system implements three distinct retrieval strategies, each optimized for different query types and user needs.

\subsection{Baseline: Cypher-Only Retrieval}
The baseline strategy relies exclusively on parameterized Cypher queries executed against the Neo4j knowledge graph. This approach offers:

\textbf{Advantages:}
\begin{itemize}
    \item High precision for structured queries
    \item Deterministic, reproducible results
    \item Efficient execution with indexed lookups
    \item No embedding computation overhead
\end{itemize}

\textbf{Limitations:}
\begin{itemize}
    \item Requires exact entity matches (mitigated by fuzzy matching)
    \item Limited semantic understanding of query variations
    \item Cannot discover ``similar'' or ``related'' entities
\end{itemize}

\subsection{Embeddings: Semantic Retrieval}
The embedding-based strategy enables semantic similarity search through text-constructed player representations.

\subsubsection{Player Description Generation}
The \texttt{EmbeddingManager} converts player statistics into natural language descriptions optimized for embedding:

\begin{lstlisting}[language=Python, caption={Player Description Template (Simplified)}]
def create_player_description(self, player_data: Dict[str, Any]) -> str:
    name = player_data.get("name", "Unknown")
    position = player_data.get("position", "player")
    team = player_data.get("team", "a Premier League club")
    total_points = player_data.get("total_points", 0)
    goals = player_data.get("goals_scored", 0)
    assists = player_data.get("assists", 0)
    
    description = f"{name} is a Premier League {position} playing for {team}. "
    description += f"In this season, they scored {total_points} FPL points "
    description += f"with {goals} goals and {assists} assists. "
    # ... additional statistical details
    return description
\end{lstlisting}

\subsubsection{Similarity Search}
The semantic search process:
\begin{enumerate}
    \item Encode user query using the selected model
    \item Compute cosine similarity against all player embeddings
    \item Rank and return top-$k$ results with similarity scores
    \item Optionally filter by season, position, or exclude specific players
\end{enumerate}

\begin{equation}
\text{similarity}(\mathbf{q}, \mathbf{p}) = \frac{\mathbf{q} \cdot \mathbf{p}}{\|\mathbf{q}\| \|\mathbf{p}\|}
\end{equation}

where $\mathbf{q}$ is the query embedding and $\mathbf{p}$ is a player embedding.

\subsection{Hybrid: Combined Retrieval}
The hybrid strategy synergistically combines both approaches:

\begin{algorithm}[H]
\caption{Hybrid Retrieval Strategy}
\begin{algorithmic}[1]
\Require User query $Q$, Intent $I$, Entities $E$
\State $\text{kg\_context} \gets \text{ExecuteCypherQuery}(I, E)$ \Comment{Structured retrieval}
\If{$I$ requires semantic expansion}
    \State $\text{key\_player} \gets \text{ExtractPrimaryEntity}(E)$
    \State $\text{similar} \gets \text{FindSimilarPlayers}(\text{key\_player})$
    \State $\text{embed\_context} \gets \text{FormatEmbeddingResults}(\text{similar})$
\EndIf
\State $\text{full\_context} \gets \text{Merge}(\text{kg\_context}, \text{embed\_context})$
\State \Return $\text{full\_context}$
\end{algorithmic}
\end{algorithm}

This approach is particularly effective for queries like:
\begin{itemize}
    \item ``Find players similar to Mohamed Salah'' (embedding-primary with KG validation)
    \item ``Best midfielders for differential picks'' (KG stats + embedding similarity)
    \item ``Consistent performers with high creativity'' (semantic matching + statistical backing)
\end{itemize}

    \item \textbf{Comparison Prompts}: Side-by-side player analysis
    \item \textbf{Trivia Prompts}: Fact verification and hint provision
\end{itemize}

\subsection{Fallback Handling}
When retrieval fails or returns empty results, the system:
\begin{enumerate}
    \item Informs the LLM that context is unavailable
    \item Instructs the LLM to acknowledge the limitation
    \item Prevents hallucination by grounding responses
\end{enumerate}

\subsection{Evaluation Framework}
The \texttt{evaluate\_llm\_models.py} script (824 lines) provides a comprehensive evaluation framework for assessing LLM performance on FPL Q\&A tasks.

\subsubsection{Test Case Design}
Test cases are designed to replicate real user interactions across categories:

\begin{lstlisting}[language=Python, caption={Test Case Definition}]
@dataclass
class TestCase:
    id: str                      # Unique identifier
    category: str                # Query category
    question: str                # User question
    expected_keywords: List[str] # Keywords for scoring
    context_query: str           # Cypher query method
    context_params: Dict         # Query parameters
    expected_answer_hint: str    # Ground truth hint
    retrieval_mode: str          # cypher/embedding/hybrid
\end{lstlisting}

\subsubsection{Metrics}
The evaluation captures both quantitative and qualitative metrics:

\textbf{Quantitative Metrics:}
\begin{itemize}
    \item \textbf{Response Time}: End-to-end latency in seconds
    \item \textbf{Token Usage}: Number of generated tokens
    \item \textbf{Success Rate}: Percentage of non-error responses
    \item \textbf{Keyword Match Score}: Proportion of expected keywords present
\end{itemize}

\textbf{Qualitative Metrics (Auto-Scored):}
\begin{itemize}
    \item \textbf{Quality} (1-5): Overall response coherence
    \item \textbf{Relevance} (1-5): Alignment with query intent
    \item \textbf{Naturalness} (1-5): Fluency and readability
    \item \textbf{Correctness} (1-5): Factual accuracy against context
\end{itemize}

\subsubsection{Model Performance Analysis}

\textbf{Gemma-2-2b} demonstrated the fastest response times (average 0.90 seconds), making it ideal for real-time applications where latency is critical. However, it achieved the lowest keyword match score (67.13\%), indicating less comprehensive coverage of expected answer components.

\textbf{Mistral-7B} provided a balanced trade-off between speed (5.21s average) and accuracy (71.20\% keyword match). Its moderate token usage (399 tokens/response) suggests efficient response generation.

\textbf{Llama-3.1-8B} achieved strong keyword match performance (73.98\%) with reasonable response times (2.75s), representing an excellent balance between accuracy and speed for production deployments.

\textbf{Zephyr-7B} achieved the highest keyword match score (80.46\%) but with significantly longer response times (29.77s average) and higher token consumption (812 tokens/response). This model is best suited for batch processing where accuracy is paramount over speed.

\textbf{Qwen-2.5-72B}, despite being the largest model, achieved moderate performance (75.93\% keyword match) with 10.05s average response time, suggesting that parameter count alone does not guarantee superior performance on domain-specific tasks.

\subsection{Key Findings}
\begin{enumerate}
    \item \textbf{Universal Success Rate}: All five models achieved 100\% success rate across 18 test cases, demonstrating robust API integration and error handling in the evaluation framework.
    
    \item \textbf{Speed-Accuracy Trade-off}: A clear inverse relationship exists between response time and keyword match accuracy. Gemma-2-2b is 33$\times$ faster than Zephyr-7B but scores 13.33 percentage points lower on keyword matching.
    
    \item \textbf{Grounding Effectiveness}: Knowledge graph context significantly reduces hallucination compared to unaided LLM responses. Test cases with complete context (e.g., player stats, defender rankings) consistently achieved 100\% keyword match across multiple models.
    
    \item \textbf{Token Efficiency}: Smaller models (Gemma, Mistral) generate more concise responses averaging 377--399 tokens, while Zephyr-7B produces verbose outputs averaging 812 tokens without proportional accuracy gains.
    
    \item \textbf{Hybrid Advantage}: Combined retrieval provides broader context for complex queries, enabling accurate responses to multi-faceted questions like player comparisons and form history requests.
    
    \item \textbf{Category-Specific Performance}: Models perform best on structured queries (player stats, top scorers) with keyword scores approaching 100\%, while fixture history and team analysis queries show more variation (40--75\%).
    
    \item \textbf{Cost-Performance Optimization}: Llama-3.1-8B emerges as the optimal choice for production deployment, achieving 73.98\% keyword accuracy at \$0.78 estimated cost---only \$0.10 more than the least accurate model while being 10$\times$ faster than the most accurate one.
\end{enumerate}

\section{Conclusion and Future Work}
\label{sec:conclusion}
%==============================================================================

\subsection{Summary}
FPL FantasyTrivia demonstrates the effectiveness of Graph-RAG architectures for domain-specific conversational AI. By combining the structured precision of Neo4j knowledge graphs with the semantic flexibility of embedding-based retrieval and the generative capabilities of modern LLMs, the system delivers accurate, context-aware responses to complex FPL queries.

Key achievements include:
\begin{itemize}
    \item Comprehensive knowledge graph schema capturing FPL domain semantics
    \item Robust NLU pipeline with 16 intent types and multi-entity extraction
    \item Flexible three-mode retrieval strategy (Cypher, Embeddings, Hybrid)
    \item Interactive Streamlit application with visualization and trivia features
    \item Quantitative evaluation framework for model comparison
\end{itemize}

\subsection{Future Directions}
\begin{enumerate}
    \item \textbf{Live Data Integration}: Connect to official FPL API for real-time statistics
    \item \textbf{Fine-tuned Models}: Train domain-specific LLMs on FPL data
    \item \textbf{Advanced NLU}: Implement neural intent classification for better generalization
    \item \textbf{Persistent Vector Store}: Replace in-memory embeddings with FAISS or Pinecone
    \item \textbf{User Personalization}: Track user teams for personalized recommendations
    \item \textbf{Multi-lingual Support}: Extend NLU to non-English queries
\end{enumerate}
