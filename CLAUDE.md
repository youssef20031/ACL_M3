# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

FPL FantasyTrivia: a Graph-RAG Fantasy Premier League assistant. React/Vite frontend (`src/`) → FastAPI backend (`api_main.py`) → Neo4j knowledge graph, plus prebuilt sentence-transformer embeddings, LLMs (Groq / HuggingFace Inference), and XGBoost point-prediction models (`ml/`).

## Commands

Backend (run from repo root; modules are imported relative to it):
```bash
.venv/Scripts/uvicorn.exe api_main:app --reload --port 8000
```
Frontend (dev server on :3000, proxies `/api`, `/health`, `/ws` to :8000 via `vite.config.ts`):
```bash
npm run dev
npm run dev:live   # same, but proxies the API to the deployed site (.env.live) — no backend needed
npm run build      # tsc && vite build → dist/
```
Load or reload the graph. A full load wipes the DB (~3 min against Aura), then adds promoted teams and the current season from `data/live/` (falling back to `data/FPL_2026_2027_fixtures_fixed.csv` for the schedule when no live data exists). The UI has no load button.
```bash
.venv/Scripts/python.exe load_data.py                 # full reload
.venv/Scripts/python.exe load_data.py --current-only  # just apply data/live to the graph
```

Current-season pipeline (`pipeline/`, data in `data/live/`, gitignored; a Docker volume on the VM):
```bash
.venv/Scripts/python.exe -m pipeline.current_season   # fetch from the FPL API -> data/live/*.csv
.venv/Scripts/python.exe -m pipeline.load_current     # apply it to the graph (idempotent, ~10 s)
.venv/Scripts/python.exe -m pipeline.predict_next_gw  # refresh odds, predict the next gameweek (v4 + v3 shadow) -> data/live/
.venv/Scripts/python.exe -m pipeline.daily            # all of the above + API reload (what the VM timer runs)
```
The FPL API only shows current values, so `pipeline.current_season` archives what was known before each deadline. On every run before a deadline it appends each player's state to `$LIVE_DATA_DIR/element_snapshots/<season>/gwNN.csv`: status, chance of playing, news, price, ownership, ep_next, the gameweek's transfers in/out and price change, and set-piece orders. Every capture is kept, so the last one before the deadline matches the last prediction run. The status file has the same transfer, price-change and set-piece columns, as one current snapshot. The archive starts at GW9 2026-27. For earlier seasons the same state comes from vaastav's weekly `players_raw.csv` commits (`data/fpl_snapshots.csv`, committed; `ml/snapshots.py`), which cover 2020-21..2024-25 but only part of 2025-26. The v4 model's availability features read both, plus the status file.
Local Neo4j alternative: `docker compose up neo4j` (bolt://localhost:7687, neo4j/password).

Dependencies: `requirements.txt` is runtime-only (what `api_main.py` imports); `requirements-dev.txt` adds pytest/hypothesis and training/analysis libs. In Linux containers install CPU torch first (see the Dockerfile).

Tests live in `tests/` (mix of `unittest` and pytest + hypothesis property tests; most mock `Neo4jConnection`). `tests/test_pipeline.py` asserts on substrings of the generated Cypher, so update it when rewriting a query in `graph/queries.py`. Run one test with:
```bash
.venv/Scripts/python.exe -m pytest tests/test_fixture_service.py::TestFixtureService::test_fixture_context_creation
```
`ml/test_*.py` are ad-hoc scripts, not a suite. `npm run lint` uses `.eslintrc.cjs` (ESLint 8) and fails on any warning. `.github/workflows/ci.yml` runs the pytest suite (Python 3.11), `npm run lint` and `npm run build` on every pull request and push to main; keep test dates relative to now, since a hardcoded kickoff that has passed changes what the cache and fixture code do.

Environment caveat: `.venv` is Python 3.14, while Docker/Railway/CI use 3.11.

## Configuration

`config/settings.py` loads `.env`: `NEO4J_URI`, `NEO4J_USER`, `NEO4J_PASSWORD`, `HUGGINGFACE_API_TOKEN`, `GROQ_API_KEY` (read directly in `llm/llm_manager.py`), optional `GOOGLE_CUSTOM_SEARCH_API_KEY`/`_CX` (avatar fallback), `REDIS_URL` (trivia cache) and `AVATAR_CACHE_PATH` (default `.cache/avatars.json`). `SEASONS` in settings lists the seasons with data, including the in-progress `CURRENT_SEASON` (2026-27); season extraction ("this season" = current, "last season" = previous), defaults and the season wording in `llm/prompts.py` derive from it. `LIVE_DATA_DIR` (default `data/live`) is where the pipeline reads and writes; `ODDS_DIR` overrides where football-data.co.uk's files live (the pipeline's default is `$LIVE_DATA_DIR/odds`, `ml/odds.py`'s and the scripts' `data/odds`); `ADMIN_TOKEN` is required (as the `X-Admin-Token` header, via `services/security.require_admin`) by every state-changing endpoint: `/api/admin/reload`, `/api/data/load`, `/api/fixtures/load`, `/api/embeddings/build`, `/api/connection/*`; without it they return 404. `POST /api/query` and `POST /api/query/stream` share one per-client rate limit (`QUERY_RATE_LIMITS`, default `10/60,120/3600`; the client is the right-most `X-Forwarded-For` entry set by Caddy). `QueryRequest` caps the question at 1000 chars and keeps at most 20 user/assistant history turns of 2000 chars (other roles are dropped); list endpoints cap `limit`/`top_k` at 50; `HEALTHCHECK_URL` gets pings from the daily job. The frontend uses `VITE_API_URL` in dev only; in production `src/services/api.ts` forces relative URLs.

## Backend architecture

`api_main.py` (~2000 lines) holds nearly all routes and glue. Shared state lives in the module-level `app_state` dict, populated in `lifespan()`: Neo4j connection, LLM manager, trivia cache, player index, avatar service/image proxy, embedding manager, ML integration. Routes get the connection through the `get_neo4j_conn` dependency; the connection can also be swapped at runtime via `POST /api/connection/connect` (Settings page). Both paths go through `_attach_neo4j()`, which resets graph caches, repoints the ML integration and rebuilds the player index. If Neo4j isn't reachable at startup, `lifespan()` keeps retrying in a background task (2 s doubling to 30 s) instead of giving up. After a VM reboot Docker restarts every container at once, ignoring `depends_on: service_healthy`, so the backend often starts before Neo4j.

The Neo4j driver and the LLM clients are synchronous. Inside `async def` routes, wrap them (`await run_db(conn, q, p)`, `await asyncio.to_thread(...)`) or make the route a plain `def` so FastAPI runs it in its threadpool; a bare call blocks every other request for its full duration.

**Q&A pipeline (`POST /api/query`)** — the core flow, spread across several modules:
1. `preprocessing/intent_classifier.py` → `Intent` (rule/keyword based), and `get_query_type_for_intent()` maps an intent to a method name on `CypherQueries`. Each matching pattern adds to an intent's score, and a tie goes to the intent listed first, except that a team intent with a club in its slot beats a player intent ("How did City do?", "Newcastle United vs Manchester United"). Team patterns take clubs from `EntityExtractor.TEAMS`.
2. `preprocessing/entity_extractor.py` → players/teams/seasons/stats/positions; `get_query_parameters()` builds kwargs (a mentioned player is `player_name` or `player1`/`player2`, plus `name_pattern` for the player search). Teams and stats match as whole words, longest key first (`EntityExtractor.find_teams`), so "Coventry City" isn't Man City and "goalkeepers" isn't goals. `TEAMS` maps every club in the graph to its graph name; add each season's promoted clubs there. A word inside a club's name (`find_team_spans`) is not a player mention unless the player is named in full: "Who is the Coventry City goalkeeper?" has no player, "How did Conor Coventry do?" does. The spaCy PERSON fallback skips entities that are club names ("Leeds United", "Tottenham's").
3. The handler looks the method up with `getattr(CypherQueries, name)`, filters params by `inspect.signature`, and falls back to `get_top_players_all_positions` if required params are missing. Before that, `IntentClassifier.refine_with_entities` turns a player intent with clubs but no extracted player into TEAM_ANALYSIS (one club) or HEAD_TO_HEAD (two). A missing season defaults to `get_latest_season()` (latest season with `SEASON_STATS`). Adding a new query type means: add a static method to `graph/queries.py` returning `(cypher, params)`, then map an intent to it. Squad questions (one club, no player, plus a position or "who plays for"/"squad" wording: "Who is the Coventry City goalkeeper?", "Arsenal defenders") skip that mapping: `is_team_squad_question` in the classifier module sends them to `get_team_squad` (current `PLAYS_FOR` squad, or a past season's `SEASON_STATS` team) as `team_analysis`, with a squad leaderboard and a team card.
4. PREDICTION intent reads `data/live/next_gw_predictions.csv` (written by `pipeline.predict_next_gw`; falls back to the bundled `ml/predictions/` copy) via `services/predictions.get_predictions_df()`, which picks the path per call and re-parses when the mtime changes. Rows include FPL `status`/`news`/`chance_of_playing_next_round`; `_availability_note` passes them to the LLM. Unavailable players stay in the file with 0 points on purpose, because a missing row would fall back to live inference and show non-zero points. TOP_SCORERS questions default to `sort_by="goals"`.
5. Embeddings/Hybrid retrieval uses `embeddings/embedding_manager.py` with pickles in `embeddings/prebuilt/` (minilm, mpnet). Managers are constructed via `EmbeddingManager.__new__` so the transformer model is not loaded until a text query needs it. Pickles are rebuilt by `.github/workflows/build-embeddings.yml` (from the CSV, no Neo4j) and committed back.
6. `llm/prompts.py` `PromptTemplates.qa_template` builds the prompt; `llm/llm_manager.py` `LLMManager.generate` dispatches by the model's `provider` and walks `FALLBACK_ORDER` on quota or model-not-found errors. All live models are on Groq (`gpt-oss-120b` default, `gpt-oss-20b`, `qwen3-27b`); `RETIRED_MODELS` maps keys that browsers may still have persisted (`llama-3.3-70b`, the old HuggingFace models) to live ones. Keep it in sync with the model list in `src/pages/Settings.tsx` and the store migration in `src/store/appStore.ts`. `enforce_tied_top_scorers_in_answer` post-processes the answer.
7. **Answer cards** (`services/answer_cards.py`) fill the response's optional `cards` (typed visual blocks: `player`, `comparison`, `leaderboard`, `prediction`, `team`, `fixtures`, `season`, `pitch`) and `follow_ups` (suggested questions). `plan()` picks builders by intent and by the method that actually ran (`executed_method`, after the all-positions fallback). They use structured data only, never the LLM's text: the query rows, a few small Cypher lookups (player info, `SEASON_STATS` and `PLAYED_IN` rows, the position pool for ranks, a team's top players), season_service's cached fixtures, table, injuries, leaders and team of the week, and the predictions file. Player cards add the next 5 fixtures with FDR, price and ownership lines (`PLAYED_IN.value`/`selected`) and season xG/xA; comparisons add xG/xA rows and the next 3 fixtures. The "notable stats" highlights (streaks, position rank, biggest haul, finishing vs xG, ties, club clusters, fixture runs) are computed there as pure, tested functions. `_prepare_answer` starts `build_answer_cards` as a task right after the Cypher step, so it runs alongside the LLM call. It never raises and times out after 10 s; a builder that fails only drops its own card. Photos come from `_photo_for`, so there are no network calls. A follow-up is kept only if `IntentClassifier` routes it to the intended intent, and team follow-ups only for teams the entity extractor finds exactly (`askable_team`, which uses `EntityExtractor.find_teams` when it exists). TypeScript shapes are `AnswerCard` in `src/services/api.ts`. Older frontends ignore both fields, and the frontend treats them as empty when an older backend omits them.
8. **Best XI questions** ("best team this gameweek", "dream team GW 5") are the `TEAM_OF_THE_WEEK` intent, listed first in the classifier so it wins ties. It has no Cypher method: `_team_of_week_for_question` resolves mode and gameweek (`season_service.team_of_week_target`), the LLM gets the squad as context, and the answer carries a `pitch` card from `get_team_of_the_week`.
9. **Streaming (`POST /api/query/stream`)**: same body and rate limit as `/api/query`, which shares steps 1–6 through `_prepare_answer`/`PreparedAnswer`. The response is server-sent events: `cards` (cards plus follow-ups, as soon as they're built), `delta` (text pieces from `LLMManager.generate_stream`, Groq `stream=True` in a thread; it falls back to another model only before the first piece), `answer` (the final post-processed text, which can differ from the pieces), `done` (the full `QueryResponse`), or `error` (`{detail}`). After an LLM error it still waits for the cards. `deploy/Caddyfile` leaves this path out of `encode` (`@compressible`) so events aren't buffered.

**Graph schema** (`graph/schema.py`, `graph/data_loader.py`, `migrations/`):
- `(Player {name, name_normalized, last_team, last_season, element_id, fpl_code, status, news, chance_of_playing_next_round, …})-[:PLAYS_POSITION]->(Position)`: exactly one position, the current one. `status`/`news` are FPL's official availability (a/d/i/s/u) and team news, refreshed by the pipeline.
- `(Player)-[:PLAYS_FOR]->(Team)`: the current 2026-27 squad, from the FPL status file. Players marked `u` whose news says they left (joined/loaned elsewhere) lose it but keep `last_team`.
- `(Player)-[:PLAYED_IN {per-match stats, season, gameweek, team, was_home}]->(Fixture {season_id, gameweek})-[:PART_OF]->(Gameweek)-[:IN_SEASON]->(Season)`, plus `(Fixture)-[:HOME_TEAM|AWAY_TEAM]->(Team)`.
- `(Player)-[:SEASON_STATS]->(Season)`: precomputed per player-season **sums** (`goals`, `total_points`, `ict_sum`, `value_sum`, `games`, `appearances`, …) plus `team`/`position`. Season-level queries read these instead of aggregating `PLAYED_IN`. Averages are `sum / games`, so they stay correct across several seasons. Gameweek-level queries anchor on `Fixture {season_id, gameweek}` and expand `PLAYED_IN`; on Aura this beat relationship-property indexes, which were tried and dropped.
- `Fixture.kickoff_time` is a Neo4j DateTime on every fixture (mixed string/DateTime values sort strings first and broke "latest matches" ordering across seasons).
- 2026-27 fixtures come from the FPL API, one node per match: `id = "{fpl_fixture_id}-2026-27"`, `status` (`scheduled`/`in_progress`/`finished`), scores only once finished. Each has both relationship styles: `PLAYS_HOME|PLAYS_AWAY` (fixture service, ML) and `HOME_TEAM|AWAY_TEAM` + `PART_OF` Gameweek (historical-style queries). Queries over results must filter `home_score IS NOT NULL`, or unplayed fixtures leak in (nulls sort first under DESC). The CSV schedule (`fixture-2026-27-…` ids) is only an offline fallback and is skipped once API fixtures exist. `load_data.py` first creates Team nodes (`promoted_season`, `efl_name`) for fixture-list clubs with no Premier League history, matched against the previous Championship table in `EFL_Data_All_Seasons/` (`--fixtures-only` reloads just this part). Fixture team names follow the graph's FPL short names (`Ipswich`, not `Ipswich Town`). Consumed by `services/fixture_service.py` (spec in `.kiro/specs/date-aware-match-predictions/`). Neo4j returns its own `DateTime` type; call `.to_native()` before JSON serialization.
- The loader drops `AM` (assistant-manager chip) rows. In the graph player identity is the name string, so a few players appear under two spellings across seasons (the v4 model's features key players by FPL code instead).

**Player search & names** (`services/player_index.py`): `PlayerIndex` is built once from Neo4j at startup (`get_player_index()`) and rebuilt after a reload. It powers search-as-you-type, `resolve()` (typed name → exact DB name, used by stats/compare/images) and `mention_spans()` (player mentions in a chat question with their place in the text, used by the entity extractor; `mentions()` gives just the names). Matching uses `utils/text.normalize_name` (handles `Ø`, `ł`, …), ranks by tier then popularity (current players, career points), and corrects typos word by word with rapidfuzz.

**Avatars** (`services/avatars.py`): sources are tried in this order:
1. FPL photo URL built from the player's `code` in the FPL bootstrap feed, which is fetched once in the background. The CDN allows hotlinking at `premierleague25/.../110x140/{code}.png`; the old `250x250/p{code}.jpg` format returns 403. About 1 in 6 codes has no photo (the CDN answers 403, mostly new signings), and the feed doesn't say which. So after loading the feed, every code gets one HEAD check in the background, and `peek()`/`get()` skip codes without a photo, including FPL URLs cached before the check.
2. A single Wikipedia search (top 3 hits), kept only when the page title matches the player's name.
3. Google CSE, if configured.

Results, including misses (which expire), persist to `.cache/avatars.json`. When no source has a photo, `PlayerAvatar` shows a blank silhouette. `/api/images/proxy` only fetches allow-listed hosts, checks every redirect hop, and keeps a small in-memory LRU.

**Season dashboard endpoints** (read-only GETs, all plain `def`): `/api/season/current`, `/api/fixtures?gameweek=`, `/api/table`, `/api/injuries?team=`, `/api/team-of-the-week?mode=predicted|actual&gameweek=`, `/api/players/leaders?season=&position=&sort=&limit=` (the Players page's default table; `games` = appearances, the `points_per_game` sort needs 270+ minutes). Their logic is in `services/season_service.py`: pure functions over plain lists, plus one cached query per view (2026-27 fixtures via `PLAYS_HOME|PLAYS_AWAY`, current-squad injuries, one gameweek's `PLAYED_IN` points). They also read `meta.json`, the status file (`web_name`, photo `code`) and the predictions file from `LIVE_DATA_DIR`. The in-process cache is keyed by inputs and file mtimes, has a 5-minute TTL, and `reset_graph_caches()` clears it, which covers `/api/admin/reload`. A missing gameweek returns 404 and Neo4j driver errors return 503. Photos come from `AvatarService.peek`, falling back to the graph's `fpl_code`, so these routes never make network calls. The table is computed from fixtures with stored scores. `Fixture.home_difficulty`/`away_difficulty` are FPL's FDR, set by `pipeline/load_current.py`. Team of the week uses `services/team_optimizer.py` (pure, scipy `milp`). Predicted mode picks a 15-man squad: £100.0m budget, at most 3 per club, `i/s/u/n` and players with no predicted points excluded. It maximises expected points: the XI, the captain's points a second time, and the bench weighted by how often each slot comes on (`BENCH_WEIGHTS` 0.5/0.15/0.05 for outfield subs 1-3, `BENCH_GK_WEIGHT` 0.05; even nailed starters miss about 7% of matches). So spare cash buys a bench that plays, and the XI may give up a little for a better first substitute. The armband is then chosen over every captain/vice pair of the XI (`pick_captains`), maximising E_c + (1 − p_c)·E_v, because FPL doubles the vice when the captain doesn't play; p is `Candidate.p_play` from FPL's chance of playing (`season_service.chance_of_playing`, the rule that also scales the predictions file), so with no flags it's the top two by points. Actual mode is the Dream Team: the best XI by gameweek points, with no budget, no club limit, no bench and no captain doubling.

**Model pick review** (`services/model_review.py`, `GET /api/model-review?gameweek=`): the squad the model picked before each deadline, scored like FPL. `pipeline.predict_next_gw` calls `save_picks` after every run while the gameweek's deadline is ahead, so the last run before the deadline leaves the final pick: `$LIVE_DATA_DIR/model_picks/<season>/gwNN.json` (15 players with element, predicted points, role, captain/vice, fixture ids, opponents) plus `gwNN_predictions.csv`. The squad comes from `season_service.predicted_selection`, the function behind the predicted Team of the Week, so it's the team the page showed. GW7 predates saving: `data/model_picks/2026-27/gw07.json` was recorded by hand from the FPL app (`source: "manual"`, with a `note`; its predicted points were recomputed from data before that deadline), and a saved pick in `LIVE_DATA_DIR` wins over a committed one. `score_picks` is pure. Actual points and minutes come from the live season CSV, FPL's average and highest score from `meta.json`'s `events` (written by `pipeline.current_season`), and auto-subs follow FPL: a starter with 0 minutes is replaced by the first bench player in order who played and keeps 3+ DEF, 2+ MID and 1+ FWD (goalkeeper only for goalkeeper), and the vice-captain doubles if the captain didn't play. While a gameweek is live, a player whose fixtures haven't all finished is undecided: he isn't replaced, and an undecided bench player blocks the ones behind him. Only gameweeks whose deadline has passed are listed. The same run also saves the shadow model's (v3) pick, from the same rows and optimizer, in `model_picks/<season>/shadow/` (`variant=SHADOW`; each JSON records its `model`). The API serves only the live picks; `shadow_comparison` scores both for the shadow ledger (see ML).

**ML manager** (`services/fpl_manager.py`, `fpl_manager_planner.py`, `fpl_manager_league.py`, `pipeline/ml_manager.py`, `GET /api/ml-manager`): a season-long FPL team run by the served model (v4) under FPL's real rules, from GW9 2026-27 (`ML_MANAGER_SEASON`, `ML_MANAGER_START_GW` in `config/settings.py`).
- **Rules:** read from bootstrap-static (`Rules.from_bootstrap`, saved per season in `rules.json`):
  - GBP 100.0m, 15 players, 3 per club;
  - 1 free transfer a gameweek, banked up to 5, 4-point hits;
  - selling price = purchase price + half the rise;
  - two of each chip, one per half: wildcard and free hit GW2-19 and GW20-38, bench boost and triple captain GW1-19 and GW20-38;
  - one chip per gameweek. The free hit reverts the squad and bank; wildcard and free hit keep the banked free transfers.
- **Engine:** `services/fpl_manager.py` is pure:
  - it validates, applies and scores each gameweek's entry;
  - scoring reuses `team_optimizer.apply_auto_subs`; the vice takes the armband if the captain didn't play, and bench boost counts all 15;
  - `replay` rebuilds the state.
- **Files:** each gameweek is `$LIVE_DATA_DIR/ml_manager/<season>/gwNN.json`. Its status goes planned, then locked at the deadline (`save_entry` refuses any change to the decisions after it), then scored with `result`. `state.json` is a derived cache.
- **Start:** GW9 is the model's saved GW9 pick (`model_picks/<season>/gw09.json`, bought at its `cost`).
- **The daily cycle:** `pipeline.ml_manager.run`, called by `pipeline.daily` after the predictions, never raises:
  - it locks plans whose deadline passed;
  - a gameweek nobody planned plays the previous team (`rollover_entry`);
  - it scores gameweeks FPL has finished and checked;
  - it ranks the running total in FPL's system league "Gameweek 9" (id 275 + N, the managers who started that week) by a binary search over its standings pages, cached in `league_cache.json`;
  - it plans the next gameweek.
- **Planner:**
  - **Inputs:** `projections.csv`, which `pipeline.predict_next_gw` writes for the next 4 gameweeks. GW+1 is the live predictions; later gameweeks reuse the deadline's feature state with that gameweek's fixtures, and availability decays.
  - **Solve:** a multi-period MILP (scipy `milp`) over that horizon, with selling prices, the bank, banked free transfers, at most 2 hits a gameweek, and a 0.9 decay per gameweek ahead. Only this gameweek's moves are kept, and it replans every run until the deadline.
  - **Chips:** a chip is played only when its solve beats the plan without it, by the module's thresholds (`TRIPLE_CAPTAIN_MIN_POINTS` and the rest), or late in its window if it still helps.
  - **Armband:** captain and vice come from `pick_captains`.
  - **Checks:** every plan passes `validate_entry` before it's saved.
- **Page:** the Team of the Week's **ML manager** tab (`mode=manager`, `components/totw/MlManager*.tsx`) shows:
  - the planned or played team with its moves and the plan's one-line `reason`;
  - free transfers, bank, team value and chips;
  - the season total, rank and percentile among the GW9 starters, and points against the gameweek average (chart and history).
  
  `/api/ml-manager` returns 404 until GW9's entry exists.

**Model explainability** (`services/explain.py`, `ml/lime_tabular.py`; `GET /api/ml/explain/summary`, `/player?element=|name=`, `/dependence?feature=`, `/players?q=`, all plain `def`): explains the served model's next-gameweek predictions (v4, or v3 until a v4 file exists; the shadow isn't explained) on the `/model` page. Every `pipeline.predict_next_gw` run writes `$LIVE_DATA_DIR/next_gw_features.csv` (`save_model_inputs`): the model's input row for each upcoming fixture plus its raw output `model_points`, at full precision, because tree splits sit exactly on training values such as 1/3 and rounding to 6 digits moved 30% of predictions by up to 0.6. Nothing else is precomputed. SHAP is XGBoost's own TreeSHAP (`Booster.predict(pred_contribs=True)`, no `shap` package), computed for all rows at once and cached by the file's and the served model's mtimes; the base value plus a row's SHAP values equals its raw output. LIME is a numpy reimplementation of `lime`'s LimeTabularExplainer defaults (quartile bins, 5000 perturbations resampled from this gameweek's rows, kernel width 0.75·sqrt(#features), highest-weights selection of 10 features, weighted ridge), seeded per row so a player's explanation is stable. The `lime` package would pull scikit-image into the runtime image. The player view also returns the steps from the model's output to the site's number (floor at 0 per fixture, double gameweeks summed, × FPL chance of playing via `availability_factor`). If the inputs file is missing, lacks a feature the served model uses, or its `model_points` no longer match the served model (a retrain with no prediction run after it), every endpoint returns 503 until the next run; an unknown player or feature returns 404. Labels, groups and descriptions of the features are in `feature_info` (v4's additions are the Team ratings, Transfers, Bookmaker forecasts and Availability groups); `tests/test_explain.py` checks that every model feature has one and that none uses betting words: the site describes bookmakers' prices neutrally ("Bookmakers' implied win chance"). The summary's `test_metrics` hold the model's own metrics under its version (`v4`), then the baselines; `ModelFacts` keys on `model.version`.

**Page-view analytics** (`services/analytics.py`): cookie-free and aggregate-only, with no IP, user agent or identifier stored. `POST /api/analytics/pageview {path, referrer}` returns 204 and is sent by the frontend only after cookie consent. The path is reduced to its lowercase route (no query/hash or trailing slash, `^/[a-z0-9\-/]*$`, at most 64 chars, anything else becomes `/other`); the referrer becomes its host and is dropped when it matches the request's Host. The endpoint is rate-limited by `PAGEVIEW_RATE_LIMITS` (default `60/60,600/3600`). `PageViewStore` keeps per-UTC-day counts in memory and writes `$LIVE_DATA_DIR/analytics.json` atomically, at most every 10 s and on shutdown. It keeps 400 days and up to 200 paths/referrers per day (the rest pool into `/other`/`other`); a corrupt file is renamed to `.corrupt` and counting starts over. `GET /api/admin/analytics?days=30` (1..400, `require_admin`) returns `total_views`, zero-filled `by_day`, and the top 20 paths and referrers.

**ML** — the production model is **v4** (`ml/points_model.py`, `ml/models/points_v4.json` + `_meta.json`, XGBoost native JSON, `MODEL_VERSION`), since 2026-10-28. Until a v4 file exists (it's trained in CI), `pm.active_model_paths()` falls back to v3. The previous model, **v3** (`points_v3.json`, `pm.V3_FEATURES`, `SHADOW_VERSION`), is kept as a **shadow**: no longer retrained, but scored on every prediction run so the two can be compared on gameweeks nobody selected on.
- **Data:** one row per player per fixture; the target is that fixture's points.
- **Features** (`build_features`) use only earlier gameweeks: rolling player form over 3 and 6 matches, the previous match on its own (`minutes_r1`, `started_r1`, `total_points_r1`), season to date, and team/opponent goals and xG over 6 and 20 matches (`team_gf`, `team_gf20`, ...) from a per-team-per-match table. Both fixtures of a double gameweek share pre-deadline values. The predicted fixture adds home/away, rest, fixtures in the gameweek, price and ownership rank. That is v3 (72 columns). v4 (`pm.feature_columns("v4")`, 96 columns) keys a player's matches by his FPL code (`player_key`: `data/player_codes.csv` plus the status file's codes), so a renamed player keeps his history, and adds 24 columns built from `pm.ExtraInputs` (`pm.load_extra_inputs`):
  - opponent-adjusted team ratings (`ml/fixture_strength.RATING_FEATURES`, `rt_*`). Serving builds from 3 seasons, so it passes the earlier seasons' team-match table as `ratings_prior` and gets training's ratings;
  - transfer-market ranks and price changes (`ml/market.FEATURES`): the history's transfer counts, and for upcoming rows the status file's `transfers_in_event`/`transfers_out_event`;
  - pre-deadline bookmaker odds (`ml/odds.FEATURES`): implied win and draw chance, expected goals for and against (Poisson fit of 1X2 plus over/under 2.5), clean-sheet chance;
  - FPL availability before the deadline (`ml/snapshots.AVAIL_FEATURES`, `snap_*`), but not the set-piece flags.
  Without `extras`, `build_features` gives exactly v3's values.
- **Odds data:** football-data.co.uk's season files (`E0_{yyyy}.csv`) for training and its `fixtures.csv` (Premier League rows) for upcoming matches, in `ODDS_DIR`. They're free for private, non-commercial use and not licensed for redistribution, so they're never committed. `python -m scripts.data.fetch_odds` downloads them (CI), and on the VM `pipeline.current_season.refresh_odds` does it at the start of every prediction run (this season and `fixtures.csv`; past seasons once). Pre-closing prices are collected by Friday 17:00 (weekend matches) and Tuesday 13:00 UK time (midweek) and count only when that's before the deadline. A run before the collection predicts with NaN odds, so the VM timer adds runs on Fridays at 17:15 and Tuesdays at 16:00 UK time (`deploy/install-daily-job.sh`; `FPL_FRIDAY_SCHEDULE`/`FPL_TUESDAY_SCHEDULE` move them): the 06:00/18:00 UTC runs miss Tuesday-evening deadlines and, in summer, Friday's prices. `tests/test_daily_job.py` checks that every kind of deadline gets a run with prices. v4 refuses to train when under half its rows have odds, overall or in any finished season (`odds_gaps`). The season in progress is exempt because its file can lag.
- **Availability data:** `data/fpl_snapshots.csv` (committed), our `element_snapshots` archive, and the status file at its `fetched_at`. Each gameweek uses the last snapshot before its deadline. Predictions keep production's chance-of-playing multiplier (`availability_factor`) on top, as the backtest's `cop` variants did.
- **Inference** appends "upcoming" rows to the same function, so training and serving can't drift apart.
- **Excluded:** FPL's historical `xP` is deliberately not a feature. It was recorded during gameweeks (it knows lineups) and leaked badly.
- **Retrain:** `python -m ml.train_points_v4` (`ml.train_points_v3.train_and_report(version="v4")`; `python -m ml.train_points_v3` still trains v3). It trains on 2020-21..2023-24, early-stops on 2024-25, tests on 2025-26 plus the current season against baselines (v4 also reports `v4_cop`, its predictions times FPL's chance of playing), then refits on everything and writes `ml/models/points_v4_report.json`. Don't train or evaluate on the user's PC (heavy jobs have crashed it): the **ML train** workflow (Actions tab, `workflow_dispatch`, `version` input, v4 by default) fetches the current season and the odds, runs `ml.train_points_<version>` and, for v4, `ml.evaluate_points_v3 --version v4`, and uploads the bundled model files plus `docs/ml_evaluation/` as the `model-<version>` artifact to commit. `ml/evaluate_points_v3.py` evaluates either version (`--version`, default v4; metrics.json keys the evaluated model as `model`).
- **Weekly retrain on the VM:** `pipeline/retrain.py` retrains v4 (refreshing this season's odds first), run by the Monday-morning daily job in a child process (v3 peaked ~0.8 GB; each attempt logs its peak). A candidate goes to `$LIVE_DATA_DIR/models/` and replaces the active model only if its held-out top-20 beats every baseline and is within 10% of the active model's (v3's recorded result while no v4 exists). Every attempt is logged in `retrain_history.json`. `pm.active_model_paths()` / `pm.load_model()` serve the live copy when present, else the bundled `ml/models/points_v4.json`. Force a run with `python -m pipeline.retrain --force` or `python -m pipeline.daily --retrain` (on the VM through `fpl-pipeline`, which holds one lock for every pipeline run). The shadow isn't retrained.
- **Shadow ledger:** before each deadline `pipeline.predict_next_gw` saves both models' squad picks, from the same feature rows, multiplier and optimizer (`model_picks/<season>/` and `shadow/`). `python -m scripts.analysis.shadow_ledger` lists their FPL points per gameweek, the difference (live - shadow), its running total and a paired bootstrap CI. On the VM, mount `scripts/` into a one-off backend container (`deploy/README.md`). Gameweeks are left out of the totals, but still listed, when:
  - both picks came from the same model (no v4 yet);
  - the two picks came from different runs (both carry one run's timestamp, `compare_picks`' `same_run`);
  - only one model has a pick.

  These gameweeks are the fresh evidence on v4, whose backtest gain didn't hold on the untouched 2022-23 fold. The shadow predicts from v4's rows, so its form features are keyed by FPL code, although v3 was trained keyed by name; this matters only for renamed players, and the backtest's `code_id` found no metric moved. A run's summary reports `odds`, `input_coverage` and `extra_inputs`. An extra input that can't be read only leaves its features NaN. A rejected weekly retrain isn't retried until the next week.
- **Evaluation:** judge changes by test top-20 pick points and captain points, not training R². Before changing features or training settings, run the **ML backtest** workflow (`scripts/analysis/ml_backtest.py`): it scores variants on four held-out seasons (2023-24 .. current) under the refit, early-stopping and weekly-retrain protocols with 3 seeds and paired bootstrap CIs, plus subsets (promoted clubs' first 6 GWs, players new from the Championship, teams within 60 days of a manager change, clubs in Europe, fixtures within 4 days of a cup tie, the first 3 matches after an absence, GK/DEF) and pick metrics (top-20 points among European clubs' players and among GK/DEF, the clean-sheet points of those GK/DEF picks, and `dnp20`, the share of the top 20 who didn't play). It also scores what the Team of the Week ships: each gameweek `best_squad` picks a squad from the predictions, scored with FPL auto-subs (`apply_auto_subs`, in `services/team_optimizer.py`): `sq_xi` (XI after auto-subs, captain once; the most sensitive squad metric), `sq_fpl` (captain doubled, vice fallback), `sq_dnp`, plus `capt_fpl`, position picks (top 4 GK / 10 DEF / 10 MID / 6 FWD) and bias by position for every variant. The top 20 is mostly midfielders, so DEF or bench effects only show there. Per-seed tables give a "single models" comparison with a two-level bootstrap (gameweeks and seeds resampled), which is what a one-seed production model experiences. The workflow's `seeds` input (e.g. `3,4,5` or `0-5`) replicates a run with fresh seeds; use it before trusting a gain that is reliable in one protocol only. `ref_seeds` (e.g. `0-19`) gives the reference more seeds; seeds run in jobs of 5 and `score --pool` merges them, and `score` also rescores saved `chunk_*.preds.parquet` files without retraining. Tried in 2026-10 and not adopted (no reliable gain over the current features): per-90 rates, a 10-match window, recency weighting, training on the last 3 seasons only, DC-points features, depth 6, `min_child_weight` 200, dropping `career_matches_before`, days since a manager change (`data/manager_changes.csv`), starting-XI rotation, and previous-Championship-season team/player stats (`EFL_Data_All_Seasons/`). The last-match and 20-match team features already capture most of what the manager and Championship data add. Also not adopted:
  - Matches in other competitions (`ml/other_competitions.py`, backtest-only: congestion around ties, minutes in the club's latest cup and all-competition matches, still-in-competition flags). Data: `data/non_pl_*.csv` from the CC0 transfermarkt-datasets dump (`python -m scripts.data.fetch_transfermarkt_non_pl`): UCL/UEL/UECL, FA Cup and super cups, 2020-21..2025-26, with no EFL Cup, no kickoff times and no 2026-27, so run those variants with the workflow's `folds` input set to `2023-24,2024-25,2025-26`. RMSE fell 0.005 (0.013 near cup ties), but neither top-20 (refit +0.056 [-0.022, +0.134]) nor captain points (+0.16 [-0.53, +0.86]) moved reliably, nor `dnp20`. Serving would also need a current-season source: the dump stopped updating in July 2026, and the only free source with all five competitions and their schedule is ESPN's unofficial, unlicensed API.
  - Form that leaves out absences (`absence_form` in the backtest: runs of 3+ 0-minute matches after regular starts, decided causally, since history has no FPL status), with or without `absent_run`/`since_return`. The model does underrate players for 3 matches after an absence (bias -0.23; -0.08 with skip + flags), but under refit overall RMSE got slightly worse and top-20 moved -0.002; only the early-stopping protocol showed a gain (+0.094 [+0.021, +0.168]), not the weekly-retrain replay. Skipping without the flags was clearly worse (RMSE +0.032).
  - An additive DC term (`code_dc`): the model learns points without DC points, and the player's recent DC points (shrunk to his position's rate, scaled on the training rows) are added back. It removed the 2025-26 DEF bias (-0.18 to -0.03) and cut rmse 0.004-0.005 on the DC seasons under refit and early-stopping. But it over-predicted MIDs (+0.05), top-20, captain and DEF picks didn't move reliably, and squad points fell 0.8-1.5 (not reliably). The DEF bias left in 2026-27 (-0.08) isn't from DC points.
  - Set-piece orders before each deadline (`ml/snapshots.SP_FEATURES`, variants `sp*`): on top of `cop` they moved top-20 by +0.01 to +0.05, none reliable, and squad points didn't move. More seasons of our own snapshot archive could revisit them and the availability features.
  - Correcting the optimizer's curse. Under refit and the weekly retrain the per-GW top 20 are over-predicted by +0.23 [+0.04, +0.41] and +0.33 [+0.15, +0.51] (single models). The bias sits at ranks 2-20; rank 1 is slightly under-predicted. Early-stopping shows no bias, with the same pick quality. Two corrections were tried. A tail shrink fitted on earlier folds only (`shrink_tail`, `shrink_tail_pos`: pred - λ·max(0, pred - κ), κ the 90th percentile) moved top-20 by -0.04 to +0.01. Refitting with the early-stopped tree count unscaled (`refit_noscale`) gave refit +0.05 [+0.00, +0.11] seed-averaged, but only +0.03 (not reliable) for single models. Neither improved squad points.
- **Adopted in v4** on the user's decision (2026-10-28), although the top-20 gain didn't hold on the untouched 2022-23 fold (the backtest's `v4` variant is the shipped feature set).
  - The shipped set against `cop` (v3 times the chance of playing, i.e. production before v4; CI run 40632554975, 2022-23..2026-27, 6 seeds):
    - RMSE fell 0.010-0.011, reliably in every protocol.
    - Top-20 rose 0.02-0.06 and squad points 0.0-0.3, none reliably.
    - Per fold, 2022-23 was again negative under refit and early-stopping, and 2023-24..2026-27 mostly positive.
  - Its evaluation (`docs/ml_evaluation/`, test 2025-26 + 2026-27): top-20 4.68 [4.36, 5.03] against 4.08 for the best baseline, and captain 7.35.
  - Odds on top of the ratings and transfer features (`odds_rt`, `odds_1x2_rt`, 6 seeds). On 2023-24..2026-27, `odds_rt` beat v3 on top-20 in every protocol: refit +0.22 [+0.11, +0.33], early-stopping +0.13 [+0.01, +0.24], weekly retrain +0.13 [+0.04, +0.23]. Over `ratings_transfers` alone the odds added little: +0.07, +0.04 and +0.09, reliable only in the weekly retrain. On the untouched 2022-23 fold top-20 was -0.06, -0.14 and +0.05, none reliable. Squad points never moved reliably.
  - `ratings_transfers` (opponent-adjusted team ratings plus transfer ranks and price changes, `ml/fixture_strength.py`, `ml/market.py`), single models, 20 seeds against 6: on 2023-24..2026-27 rmse fell 0.019 and the squad's non-playing starters 0.12-0.19 per GW in every protocol, and top-20 rose 0.11-0.13 under refit and early-stopping. On the untouched 2022-23 fold the top-20 gain was gone (early-stopping -0.20 [-0.40, -0.01]), and squad points never moved reliably.
  - Pre-match bookmaker odds alone (`ml/odds.py`, variants `odds` and `odds_close`). Pre-closing prices count only when collected before the deadline, which covers 87-91% of 2020-24 fixtures and 97-100% since. Over two seed sets (0-2, 3-5) the top-20 gain was positive in every protocol but reliable only under refit (6 seeds pooled: refit +0.105 [+0.033, +0.178], early-stopping +0.030 [-0.051, +0.107], weekly retrain +0.069 [-0.025, +0.164]). Seeds 0-2 alone gave refit +0.138 [+0.047, +0.229], seeds 3-5 +0.073 [-0.012, +0.157]. Captain points were never reliable (+0.21 to +0.34). RMSE fell 0.002-0.003. GK/DEF clean-sheet points of the top-20 GK/DEF picks rose 0.02-0.05, reliable only under early-stopping. Closing prices (after lineups, an upper bound) did no better. Serving uses football-data's `fixtures.csv`. The Odds API (free tier 500 credits/month, licence allows use in apps and models) is the alternative. Free player-level odds (anytime scorer) exist only as current prices: The Odds API has EPL props from US bookmakers, with history only on paid plans and only since 2023-05.
  - FPL availability before each deadline (`ml/snapshots.py`, variants `cop`, `avail*`, `snap_cop`, folds 2022-23..2024-25). Players listed as unavailable played 1.4% of the time, so the timing is right. Production's chance-of-playing scaling (`cop`) earns its place: without it, top-20 falls 0.05-0.07 and the squad has 0.15-0.19 more non-playing starters per GW, reliably in every protocol. On top of it the availability features were neutral (top-20 -0.001 to +0.025, rmse -0.002, none reliable), so v4 keeps the multiplier as well.
  - Players keyed by FPL code instead of name (`code_id`, `data/player_codes.csv` from `python -m scripts.data.fetch_player_codes`): 173 players' histories were split by spelling changes, but no metric moved. Adopted as housekeeping, since it corrects real data.
- **Leakage tests:** `tests/test_points_model.py` checks no row duplication, gameweek freezing, and team strength excluding the match itself. It also checks that the backtest candidates use only pre-deadline data: other-competition outcomes, and odds collected after the deadline. `tests/test_points_model_v4.py` checks v4's training/serving parity (an upcoming row's 96 features equal the same row built as history), that odds and snapshots captured after the deadline never reach a row, the code identity join, and ratings from a shorter history plus the prior.

`pipeline/predict_next_gw.py` serves v4 (or v3 until a v4 file exists) for the next FPL gameweek:
- It reads the last 3 historical seasons plus the current one. Measured against all seasons (v3): correlation 0.9998, same top 20, half the memory.
- It refreshes the odds first, then builds v4's inputs from the status file (codes, transfers, availability at its `fetched_at`), the snapshot archive and `ODDS_DIR`. A failed download only leaves the odds features NaN.
- It scores the v3 shadow on the same rows and saves its pick (see the shadow ledger). A failing shadow never affects the live predictions.
- Double gameweeks are summed; blank gameweeks get 0.
- Points are scaled by chance of playing, or set to 0 when the player is unavailable.
- It also writes the model's inputs (`next_gw_features.csv`, v4's columns, which include v3's) for the explainability endpoints.

All user-facing predictions come from that file: chat, search, `/api/ml/top-performers`, `/api/ml/best-value`, and `POST /api/ml/predict/player` via `_LazyMLIntegration`. A player missing from it isn't in the current FPL game, and gets a 404 or "no prediction", not a guess.

The legacy v2 stack is still loaded at startup by `ml/api_integration.py` (`MLAPIIntegration`, `xgboost_*_v2.pkl`, `ml/feature_engineering.py`), but only as a fallback when no predictions file exists. Its training pipeline duplicated rows about 20x through `FeatureEngineer`'s opponent merges, so don't build on it. Promoted-team handling there uses EFL data in `EFL_Data_All_Seasons/`.

## Frontend architecture

The site is branded **Pitch Me** (FPL-inspired, never using Premier League/FPL marks). Routes in `src/App.tsx`, all under `components/shell/AppShell.tsx` (sticky `SiteHeader` with a "More" menu, `DeadlineBar` from `/api/season/current`, `SiteFooter` with the not-affiliated disclaimer, `PlayerSearchDialog` opened by the header or `/`):
- `/` Home dashboard, `/fixtures?gw=`, `/table`, `/team-of-the-week?mode=actual|review&gw=`, `/players`, `/predictions`, `/model?tab=overview|player|effects&player=&feature=`, `/assistant` (full-height, no footer), `/compare`, `/trivia`, `/settings`, and a 404.
- `/qa` and `/search` redirect to `/assistant` and `/players`, keeping router state. Pages pass state between each other: `/players` takes `{ player, season, returnTo, compare }`, and `/assistant` takes `{ question }` and sends it.
- `/design` (outside the shell, not linked) shows every design-system component with sample data.

All HTTP goes through `src/services/api.ts` (axios, 60s timeout; `streamQuery` reads the answer stream with `fetch`); global state in `src/store/appStore.ts` (zustand, persist version 4); TanStack Query for fetching. Pages are lazy-loaded per route; player photos render through `components/AvatarImage.tsx`. Search results carry an `avatar` when the backend knows it without a network call (`AvatarService.peek`); rows without one are filled by `hooks/usePlayerAvatars.ts`, which caches per name under `['player-avatar', name]`, shared across pages. `hooks/useHealthSync.ts` polls `['health']` and mirrors it into the store.

**Assistant** (`pages/QAAssistant.tsx`, `hooks/useAssistantAsk.ts`, `components/assistant/`): `useAssistantAsk` streams answers into the store (`addMessage` a placeholder with an `id`, then `updateMessage` with cards and rAF-batched text) and falls back to `POST /api/query` when the stream endpoint is missing (`StreamUnavailableError`). `abortAnswer()` stops it, and Clear chat calls it. The conversation is saved to session storage (`pm-chat`, version 1, the last 40 messages, finished exchanges only, not while an answer streams), so it survives a reload but not closing the tab; settings stay in the persisted zustand store. The message list isn't a live region (it would read every card out in full): a visually hidden `role="status"` announces the finished answer's plain text and each card's `cardLabel` once.

**Assistant cards** (`src/components/assistant/cards/`): `AnswerCards` renders a message's `cards` above the answer text, one component per type. An error boundary drops a card that fails to render, and unknown types are skipped. `FollowUps` shows the chips on the latest finished answer, and `AnswerCardSkeleton` holds the place until the cards arrive. `shared.tsx` holds the card frame, highlights, `MiniBars` (bars at most 24px wide with direct value labels), opponent/FDR chips, fixture strips, trend lines and `useCardPhotos` (the backend's photo, else `usePlayerAvatars`). Each card is a CSS size container, and its grids switch with `[@container(min-width:…)]:` variants rather than viewport breakpoints, because the chat column narrows when the details panel opens; write those classes out literally, since Tailwind can't see class names built from template strings. The `pitch` card uses `Pitch`'s `compact` mode. In the chat, tapping a player asks about them (`AskProvider`, `PlayerAction`), and a small icon opens their `/players` profile; with no `onAsk` (as on `/design`), players link to the profile. Card links reuse the router-state contracts above (`/players` and `/compare` `{ player1, player2, season }`). The history sent to the API stays role/content. **Save/share as image**: `ShareableCard` renders an off-screen copy of the card under `ExportProvider` (`exporting`: photos go through `/api/images/proxy` so the canvas isn't tainted, `data-export-hide` elements are dropped, and the footer becomes the Pitch Me mark). It draws the copy with a lazily imported `html-to-image` and offers the PNG to the share sheet on touch devices that can share files, or downloads it otherwise. html-to-image waits for an animation frame, so in a background tab it finishes only when the tab is visible again. `/design` shows every card type from `cards/samples.ts`.

**Model insights** (`pages/ModelInsights.tsx`, `components/explain/`, in the header's More menu and linked from /predictions as "Why these numbers?"): three tabs over the explain endpoints. Overview has mean |SHAP| bars per feature group and for the top 15 features, a beeswarm of the top 10, the model's facts with its test metrics against the baselines, and top-player chips. Explain a player has a search over `/api/ml/explain/players`, the steps from model output to predicted points (only those that change something), and per fixture a SHAP waterfall (the "N other features" bar is the remainder, so it always adds up), a LIME panel with its local R² and a SHAP-vs-LIME table. Feature effects has a SHAP dependence scatter coloured by position. Charts are hand-rolled SVG/HTML that scale with `useElementWidth`, each with an accessible summary and a "Show the numbers" table. A 503 (or a 404 from the summary) shows "Explanations appear after the next prediction run". `/design` shows all three tabs and the empty states from `components/explain/samples.ts`.

**Team of the Week tabs** (`pages/TeamOfTheWeek.tsx`): Predicted, **Model vs actual** (`mode=review`, `components/totw/ModelReview.tsx` over `/api/model-review`), Dream team and **ML manager** (`mode=manager`, see the backend's ML manager). The review shows the final XI after auto-subs on the pitch (counted points, with the prediction in `PitchPlayer`'s `detail` strip and an arrow `marker` for subs), the bench in priority order, the model's points against FPL's average and highest, and a predicted-vs-actual table of all 15 players. A 404 means no saved pick for that gameweek. Pitch name plates use the payload's `web_name` (`PitchPlayer` `displayName`). `/design` shows it with `components/totw/samples.ts` (the real GW7 pick).

**Site essentials.** Every page calls `hooks/usePageMeta({ title, description })` (document title, meta description, OG/Twitter title+description, canonical); `index.html` holds the site-level OG/Twitter tags, icon set and manifest, with `%SITE_URL%` filled at build by the `pitchme-site-essentials` plugin in `vite.config.ts`, which also emits `robots.txt` and `sitemap.xml` (route list `SITEMAP_ROUTES`). `SITE_URL` defaults to the sslip address; Docker passes `SITE_ADDRESS` as the build arg and `toSiteUrl()` takes the first address of a Caddy list (adding `https://`), falling back to the default instead of failing the build. `node scripts/site/render.mjs` regenerates `public/og-image.png` and the favicons. The consent banner (`shell/ConsentBanner`, state in `lib/consent.ts`, key `pm-analytics-consent`, GPC = declined) gates `apiService.trackPageview`, called on route changes in `AppShell`. `/privacy`, `/terms` and `/contact` describe what the site actually does; update `/privacy` if data handling changes. `deploy/Caddyfile` lists the SPA routes: listed routes get 200, unknown paths get the app's 404 page with a real 404 status, so add new routes there and to `SITEMAP_ROUTES` too.

**Design system.** Colours are CSS variables in `src/styles/tokens.css`, mapped to Tailwind names in `tailwind.config.js` (`bg`, `surface`, `brand`, `line`, `fg`, `accent` mint, `accent-2` cyan, `pos-*`, `fdr-*`; font sizes `display/h1/h2/h3/body/data/micro`; Outfit + Inter from `@fontsource`). Use the tokens only, never raw palette classes or hex. Charts and SVG use `rgb(var(--accent))`. Shared components live in `src/components/ui` (barrel `index.ts`: Button/ButtonLink, Card, PageHeader, Tabs, DataTable, badges, ClubCrest, PlayerAvatar, Pitch, FixtureRow, states); page-specific pieces go in `src/components/<area>/`. Always merge classes with `cn()` (`utils/cn.ts`), which registers the custom font sizes with tailwind-merge; without that, `text-h1` is dropped when a colour class follows. The UI is dark-only: the store migration forces `theme: 'dark'`. Light mode is a future `[data-theme="light"]` token block. Club crests are 128px PNGs in `public/logos/`. `docs/FRONTEND_REDESIGN_BRIEF.md` lists the constraints (API contract, query keys, store shape, acceptance checklist).

## Deployment

Production is one Ubuntu VM with 4 GB+ RAM (Azure for Students x86_64 now; Oracle Ampere arm64 also supported, so keep both architectures building) running `deploy/docker-compose.yml`. Neo4j memory defaults (`NEO4J_HEAP=1G`, `NEO4J_PAGECACHE=512M`) are sized for 4 GB; the backend peaks around 0.9 GB. Services: `web` (Caddy: HTTPS, serves the built `dist/`, proxies `/api`, `/health`, `/ws`, `/docs`), `backend` (root `Dockerfile`), and `neo4j` (not public). See `deploy/README.md`.
- `deploy/setup-vm.sh` does one-time VM setup.
- `deploy/deploy.sh [--load-data]` pulls, rebuilds and restarts.
- `.github/workflows/deploy.yml` runs it over SSH once the `VM_*` secrets exist.
- Because the site and API share an origin there is no CORS config; extra origins come from `CORS_ORIGINS`.
- New runtime deps must ship linux/aarch64 wheels.
- The backend image is built from the repo root, so the root `.dockerignore` must keep excluding `deploy/` (which holds `deploy/.env`).

## Repo layout notes

The root holds only entry points and config (`api_main.py`, `load_data.py`, Docker, package and build configs). Committed datasets are in `data/` (`cleaned_merged_seasons_cleaned.csv`, `FPL_20xx_20xx.csv`, the 2026-27 fixture CSVs, `manager_changes.csv` from `python -m scripts.data.fetch_manager_changes`, and `non_pl_matches.csv`/`non_pl_appearances.csv` from `python -m scripts.data.fetch_transfermarkt_non_pl`, the last three used only by the backtest; `player_codes.csv`, each season's FPL element mapped to the player's stable code, from `python -m scripts.data.fetch_player_codes`; and `fpl_snapshots.csv`, FPL availability and set-piece orders before each deadline from the git history of vaastav's `players_raw.csv`, built by `python -m scripts.data.fetch_fpl_snapshots`; the last two are v4 inputs); their paths come from `config/settings.py` (`DATA_DIR`, `DATA_PATH`, `FIXTURES_FALLBACK_CSV`) and `ml/points_model.HISTORY_CSV`, while the many older `ml/` scripts use `data/...` relative to the repo root. One-off tools are in `scripts/` (`checks/`, `data/`, `efl/`, `embeddings/`, `analysis/`; see `scripts/README.md`), run from the root as `python -m scripts.<group>.<name>`. `legacy/` holds the original Streamlit `app.py` and `api_main_old.py`, not used. Past working notes live in `docs/archive/`, describing history, not current behavior; course reports and the LLM evaluation charts are in `docs/reports/`.
